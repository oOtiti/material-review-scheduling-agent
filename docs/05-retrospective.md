# 复盘与迭代

核心难点是把模型建议、用户授权和实际写入分别落到可验证的数据上。提案绑定审核证据和时段，执行器复查后才写入。这样可以在替换模型、调整提示词或引入新知识时，继续用相同的业务断言比较结果。

每次改动先选择一条可复现的失败 Trace，写入回归用例，再调整一个变量，例如规则、提示词或案例库。跑完整离线核心集和配对模型路径，与同套样本的基线比较，记录新增失败、裁判分歧和工具调用变化。经过人工复核的案例才能进入案例文件。若回归失败，保留当前版本和证据，恢复到最近通过的配置。

本次迭代从真实小模型重复审核开始。候选菜单排除已读取的证据，修复了停滞。之后从档期冲突用例发现模型可能过早提案，于是先写回归测试，再让执行器拒绝并返回原因。最后重跑同一对真实用例。记录首次动作和恢复动作便于评审分别判断模型决策和执行器兜底。

提交前的独立 AI 评估发现，固定步进可能漏掉从已有排期结束时刻开始的空档。回归测试先复现了错误阻塞，再将同一资源的排期结束时刻加入候选起点，并复查窗口和占用。复核后的用例能找到唯一可用的 14:15–14:45。

AI 生成代码的质量用结果检验。运行规则集中在工作流和存储，模型层只处理动作提议，CLI 只处理输入输出。改动应保留字段契约，具备可复现的测试证据，并由维护者复查异常路径、依赖与命名。现阶段证据覆盖小型合成场景，实际多人授权、IM 回调和生产档期数据需要在接入时做相应验证。
