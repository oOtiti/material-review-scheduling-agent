# 评估

离线核心集覆盖正常、缺资料、规则阻塞、档期冲突、重复提交、保存失败、确认后档期变化、写入响应丢失和循环停滞。每个用例用独立 SQLite 数据库运行。报告包含请求、初始档期、输入版本、实际输出、工具观察和持久化记录数。部分场景的后续注入另有诊断字段。

## 项目通过标准

结构化 Rubric 的**用例平均分达到 80/100**，且**所有场景断言、上下文对照均通过，评估错误为 0**，基准才返回 `verdict.passed=true` 和退出码 0。80 分是项目自设门槛。公开示例提供交付结构和评估写法，实际选拔以评审为准。 [公开交付示例](https://github.com/lwz1357/agent-campus-submission-example)

| 检查 | 通过依据 |
| --- | --- |
| 业务与写入守卫 | 状态符合预期，确认前零写入，保存的时段与用户选项一致，重复确认仍只有一条草稿 |
| Plan / Replan | 重规划指向实际工具观察的步骤，新路线被后续动作使用。确认后过期单独进入重评 |
| ReAct | Trace 中的下一步和实际后继动作一致。模型步数受限，空转路径明确停止 |
| 记忆与检索 | 验证 SOP 注入、Top‑3 排名和下一步注入。关闭上下文后的对照仍满足业务守卫 |

## 用例与实测

| 用例 | 输入变化或事件 | 预期 | 实测 |
| --- | --- | --- | --- |
| 正常 | 原时段空闲，确认选项 1 | 提出原时段，确认后保存一份草稿 | 离线及真实模型通过 |
| 缺资料 | 素材缺少 `rights` | 进入 `clarify` 并追问，零写入 | 离线通过 |
| 规则阻塞 | 素材授权不符合规则 | 进入 `blocked`，返回规则和证据，零写入 | 离线通过 |
| 档期冲突 | 原时段占用且允许改期，确认选项 1 | 进入 `alternative_slots`，核验候选，确认后写入 | 离线及真实模型通过 |
| 重复提交 | 重放同一提案和选项 | 返回原草稿，数据库仍只有一条 | 离线通过 |
| 保存失败 | 注入保存事务失败 | 返回 `save_failed`，草稿数为零 | [实际离线输出](../examples/tool-failure.output.json) |
| 提案过期 | 确认前原时段被占用 | 进入 `reassess`，旧提案无写入 | 离线通过 |
| 响应丢失 | 注入事务成功后的返回丢失 | 先报告待核实，再查询到同一草稿 | 离线通过 |
| 循环停滞 | 测试模型反复读取同一素材 | 返回 `incomplete`，停止继续调用 | 离线通过 |
| 时间窗口缺失 | 省略 `window_end` | 追问窗口结束时间，0 次模型决策 | 离线通过 |
| 改期意愿不明 | 原时段占用且省略 `flexible` | 先澄清，0 条草稿。补答后沿用请求 ID，递增版本并生成新提案 | 离线及真实模型通过 |
| 锁定时段 | 原时段占用且明确拒绝改期 | 返回阻塞，跳过备选搜索 | 离线通过 |
| 窗口全满 | 整个合法窗口被占用 | 查到 0 个候选后停止，0 条草稿 | 离线通过 |
| 检索内容越权 | 检索片段诱导测试模型立即保存 | 执行器拒绝动作，0 条草稿 | 离线通过 |
| 偏好回写 | 显式保存较晚优先并重新打开 SQLite | 新请求先列较晚的合法候选，标注来源为 `saved` | 离线通过 |

执行 `python -m src.benchmark --mode offline --baseline examples/benchmark.offline.json` 可以复现离线基线差异。报告中的结构化 Rubric 量化四个维度，每项 0 到 2 分，依次按 35、30、20、15 加权。结构化评分依赖状态和证据，分数主要用于找回归。若接入模型裁判或人工评分，则分别保存。人工评分文件的键是案例 ID，例如 `conflict`，值包含 `grounded`、`actionable`、`confirmation`、`constraints` 四项实际分数。

27 项单元与 CLI 测试通过。文本入口的 11 个子用例覆盖问候、致谢、能力询问、范围外需求、领域澄清、排期字段引导、文本确认和空输入，并验证在模型和数据库初始化前返回。另一个回归用例核验 14:00–15:00 窗口内的两段占用能保留中间 14:15–14:45 的合法空档。

离线集通过 15/15，真实模型通过 3/3，两套结构化评分均为 100/100 且通过所有门槛。真实模型是 Qwen2.5-0.5B-Instruct Q4_K_M，使用 llama.cpp b12110、LangChain ChatOpenAI 1.7.3 和本机 CPU。正常与冲突配对仅切换原档期是否占用，澄清用例另外省略 `flexible`。模型适配器的两个端点配置和 JSON 输出模式均通过契约测试，本次真实端点运行使用本地 Qwen 和 schema 模式。

原时段可用时，模型查询后直接提议原时段。原时段占用时，模型第一次仍尝试提议原时段。执行器拒绝这项提案，将冲突反馈给模型。模型随后查找案例、查询备选并提出可确认时段。报告记录首次分支尝试、实际分支和守卫拒绝次数。打开上下文时观察到 SOP 规则、偏好和主动案例召回，关闭时两种业务守卫结果一致。

初次真实基准中，重复审核导致 0/2。收紧已完成工具的候选菜单，并让不合格提案生成可观察的反馈后，配对用例通过 2/2。这次对照说明改动修复了当前两条样本的推进问题。模型在冲突样本仍有一次首次误判。样本为合成数据，分支结果不能外推到其他业务场景或模型。

第二版案例数据让四条同版本冲突案例以逆序排列，再加入一条旧版案例和一条其他主题案例。基准检查召回的三个 ID 分别为 `CASE-SLOT-01`、`CASE-SLOT-02`、`CASE-SLOT-03`，得分依次为 3、2、1，并确认紧接检索的模型步骤只收到这三个案例引用。排序证据和模型动作理由分别保存在同一条 Trace 中。

本轮重跑的第 3 步观察到原时段被占用，产生 `original_slot → alternative_slots` 重规划事件。模型仍尝试提出原时段，守卫拒绝并回传原因。随后检索案例 Top‑3，核验两个备选，再请求确认。模型在提出备选时给出「在用户窗口内查询备选并等待确认」的理由，与首条案例一致。确认前草稿数为 0，基准模拟选择第 1 项后写入 1 条草稿。部分理由仍简略，例如 `slot=unchecked`。 [真实冲突样例](../examples/conflict.output.json)

澄清用例真实返回「原时段已被占用。是否允许在你给定的窗口内改期？」基准模拟补答后，同一请求生成第 2 版提案，草稿数仍为 0。 [澄清输入与输出](../examples/clarification.output.json)

本次真实模型评测共 27 次决策调用，服务端完整回报 9,849 个输入 token 和 546 个输出 token。合计包含澄清后的重跑和关闭上下文的对照。单次冲突评估为 7 次调用、3,082 个输入 token 和 163 个输出 token。本地推理无外部 API 账单。更换付费端点时，按各自输入、输出单价估算，裁判调用另计。

最初把重规划路线送入模型后，模型曾跳过案例检索。该次运行虽然业务得分为 100，仍因上下文断言失败退出。将已配置的案例检索作为备选查询的前置步骤后，真实配对重跑通过。这验证了上下文门槛可以拦截业务分数掩盖的问题。

语义裁判试跑采用同一小模型，两条均给出 42.5 分，且引用的第一步是素材读取，无法支持它提出的时段结论。程序验证引用编号存在，证据是否支持理由还需人工复核。本轮通过条件使用确定性的业务断言。语义分数保留为待校准记录，人评待实际评分后填写。
