# 方案

## SuperAgent 的分工

一个工作流统筹规划、工具、记忆和持久化。代码规划器负责目标、依赖和重规划，LangChain 模型负责逐步选择动作，审核和排期工具提供事实，状态机负责授权、终止条件和保存。各模块通过结构化事件协作，CLI 是当前入口。

CLI 的 `chat` 用本地规则回复常见问候、拒绝范围外请求，或澄清是否为内容发布排期。明确的排期意图会收到提交字段与示例。文本入口直接返回，任务评估由 `start` 开始，写入由携带提案身份和选项的 `confirm` 触发。

| 阶段 | 输入和产出 |
| --- | --- |
| Plan | 根据请求和 SOP 建立审核 → 档期 → 提案确认 → 草稿保存的目标及依赖。初始路线为 `original_slot` |
| ReAct | 每轮将当前路线、工具观察摘要、相关记忆和允许动作交给模型。模型返回一个动作及简短理由，执行器校验并运行，结果进入下一轮 |
| Replan | 可信工具观察改变后，代码规划器生成 `replans` 事件，记录原路线、新路线、触发步骤、原因和剩余目标。下一轮模型收到新路线和更新后的动作集合 |
| 守卫与恢复 | 候选必须来自已核验的时段。守卫拒绝的提案把原因回传给模型。用户确认绑定提案版本和选项，保存前复查审核和档期，SQLite 负责事务及去重 |

## 执行路径与结束条件

| 观察或事件 | 路线和后续动作 |
| --- | --- |
| 素材资料不足 | 切到 `clarify`，提示补齐具体字段 |
| 审核被拦截 | 切到 `blocked`，返回规则与证据 |
| 原时段可用 | 保持 `original_slot`，提议原时段并等待确认 |
| 原时段被占用且允许改期 | 切到 `alternative_slots`。启用上下文时先完成案例 Top‑3 检索，再开放窗口内的备选查询。关闭上下文的对照直接查备选 |
| 原时段被占用，改期意愿缺失 | 切到 `clarify`，追问是否允许在原窗口内改期。补充 `flexible` 后用原请求编号发起新评估 |
| 原时段锁定或无合规备选 | 切到 `blocked`，说明无法满足当前要求 |
| 确认时审核或档期变化 | 切到 `reassess`，旧提案失效。用户重跑原请求生成新版本，再确认 |
| 保存失败或结果未知 | 分别返回可重试或待核实的状态，重试和查证使用原请求 |
| 动作空转或达到预算 | 停止本轮并返回 `incomplete`。每次评估最多 8 次模型决策，另设 12 次工具调用上限 |

以冲突路径为例，`query_slot → occupied` 触发外层重规划。下一轮使用新路线，模型在 ReAct 循环内选择检索案例和查询备选。两层都留有记录，因此可以从一次运行看出计划如何变、模型做了什么，以及确认和保存发生在何处。

备选时段从用户窗口内的步进起点及同一资源的已有排期结束时间中生成。候选去重后逐一核验持续时长、窗口和占用约束，因此可以找到从 14:15 这类非步进边界开始的空档。

| 字段 | 由谁提供 | 为什么保留 |
| --- | --- | --- |
| `request_id`、`revision` | 请求和任务存储 | 跨进程关联一次任务，重评递增版本 |
| `material_id`、`resource` | 请求 | 精确定位素材和排期资源 |
| `preferred_start`、`slot_minutes` | 请求 | 表示首选区间，生成带明确偏移的半开区间 |
| `window_start`、`window_end`、`flexible` | 请求 | 在硬性时间范围内生成候选，`flexible=false` 锁定原时段。缺省或 `null` 时，原时段冲突才追问 |
| `proposal_id`、`choice` | 执行器与用户操作 | 确认绑定版本、审核证据和具体时段，防止保存另一份提案 |
| `rule_id`、`rule_version`、`evidence_version` | 规则工具 | 保存时用当前素材及规则复查，变更后需要重评 |
| `plan[].sources` | 代码规划器 | 记录目标来自 SOP、请求、工具结果或确认事件 |
| `plan_route`、`replans[]` | 代码规划器 | 记录当前路线和每次重规划的触发步骤、原因与剩余目标 |
| `trace[].plan_route`、`next_action` | 执行器 | 将每个实际动作对齐到当时的路线和下一轮动作 |
| `trace[].context_sources` | 运行时 | 区分 SOP 注入、工具观察、主动检索。记录送入模型的来源 |
| `draft_id`、`saved_slot` | 持久化结果 | 说明写入发生在哪条草稿，支持重复确认与查证 |

审核阶段被动注入当前规则卡片，档期阶段注入当前允许窗口。原时段占用且允许调整时，SOP 还会注入适用的排期偏好，Agent 可以主动检索同类案例。召回按主题和规则版本过滤。案例和用户偏好只参与提示或排序，硬约束始终由工具核验。当前的合成用户偏好由请求选择。规划来源表示计划用到的输入类型，Trace 表示实际提供的上下文，两者都保留给评审检查。

记忆分三层。SQLite 保存请求、提案、候选、状态和 Trace，下一次 CLI 调用可以恢复。用户通过 `remember-preference` 显式回写偏好，同一数据库和同一 profile 的后续请求优先读取已保存值，示例 JSON 提供默认值。允许改期时偏好才参与已核验时段的排序。案例由版本化 JSON 管理，包含主题、适用规则版本、资源、档期时长和处理经验。

案例检索采用可解释的元数据排序。冲突场景先筛选同主题、同规则版本的案例。同资源加 2 分，时长相同加 1 分，按分数降序、案例 ID 升序取 Top‑3。通用案例得 0 分，可在更匹配的案例不足时补位。检索结果将案例 ID、内容片段、匹配项和分数一并提供给下一轮模型。当前知识库使用本地合成案例，检索基于元数据匹配。

Trace 分别保存工具的实际观察、提供给模型的来源、模型对动作给出的简短理由，以及状态机的拒绝反馈。来源记录表明模型收到了哪些内容。模型是否有效使用它们，还需要将理由和行动与实际工具观察对照。

系统提示声明动作格式与确认边界，SOP 负责注入当前规则和合法时间窗口。检索片段进入模型的数据上下文。执行器再次校验动作权限，并独立核验用户确认。模型输出的权限声明只作为文本处理。

SQLite 对确认与草稿保存开启写事务，以请求 ID 唯一约束写入。保存失败在事务内回滚，响应未知时按同一请求查询。档期数据作为每次 CLI 调用时载入的快照，草稿保存不占用正式排期。如果升级为多人服务，应把档期、草稿和事务边界移到同一个可信存储，或在独立服务里使用版本化条件写入。

未来接入 IM 时，适配器验签后由服务器提取 `tenant_id`、`actor_id`、`event_id` 和会话来源。入口对事件去重，并校验用户是否能访问该素材、该排期资源及当前提案。确认事件必须对应授权人和提案版本。IM 消息、引用和知识库文档只作为输入。主动接收多来源事件时，可以借鉴 DeepSeek Super Agent 原型的来源规则与宿主授权。 [DeepSeek Super Agent 授权设计](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/main/docs/002-authorization.md)
